\easrptitle{Creating and Sharing Genomic Annotation Modules with AI Agents:
From Assisted Authoring to an Autonomous Curation Loop}

\begin{document}

\maketitle

\begin{abstract}
Genome analysis is an iterative workflow (ask, select data, score, annotate,
inspect, and revise), and it is increasingly done inside AI coding assistants
rather than in fixed graphical interfaces. But general-purpose language models have been shown to be
unreliable when used directly for genomics: to fabricate variant identifiers,
misassign effect directions, and attach real PMIDs to the wrong paper. The
Just-DNA ecosystem redirects these assistants from generating disposable code to
producing structured, versioned data: \emph{genomic annotation modules} where
every variant is linked to its genotype and can carry its evidence, effect
size, and a verbatim passage from the source paper. The output is an editable data artifact that a domain
expert can review in a spreadsheet without specialized tools.

This paper presents the plugin ecosystem that makes this possible. The
authoring plugin, \textbf{just-module-creator}, runs inside the AI coding
assistants that bioinformaticians and developers already use daily, so module
authoring requires no new infrastructure. The underlying toolchain validates
authored files against a live schema, checks identifiers against reference
databases, and compiles modules into a portable artifact. A shared registry lets
independent authors publish, version, and exchange modules---the package-registry
pattern applied to genomic annotation knowledge. We also show the plugin as the
authoring end of an autonomous research loop: over two weeks, several agent
roles re-curated a 164-row longevity module, reading the literature, writing
each row with verbatim evidence and rehearsing every version, while a
non-blocking, asynchronous human-in-the-loop design confined the maintainer to
decisions and irreversible steps. The three scored authoring runs are archived
with their inputs and re-score exactly. Against the same model working from
the documentation or from example modules, on three papers with two models, no
run cited a nonexistent paper; all six of the plugin's modules passed the
format's strict validation, while eight of the twelve built without it failed
validation or placed no variant on the genome. Applying a module to a genome is the
work of the annotation consumer, Just-DNA-Lite, the subject of a companion
paper~\citep{companion2026justdnalite}. The software is open-source and available at
\url{https://github.com/dna-seq/just-module-creator}.
\end{abstract}

\section{Introduction}
% ================================================================

Genomic annotation connects variant calls to the knowledge that gives them
meaning: trait associations, clinical classifications, effect sizes, and the
evidence behind each claim. This knowledge is scattered across papers, databases,
and preprints, and it changes as new studies appear. Turning it into something a
computational pipeline can use requires structured, validated records with
unambiguous variant identifiers, genome-build coordinates, and traceable
citations.

The wider setting is personal genomics. Genotyping and sequencing now reach
individuals directly, and research into how individual variation shapes
traits, drug response, and ageing depends on curated knowledge that keeps pace
with the literature. Most of that knowledge is assembled by hand, by a few
groups, for a few domains. This paper is written for the people who build such
resources: bioinformaticians and computational biologists who curate variant
knowledge, and developers of AI agents for scientific work. It is not addressed
to individuals reading their own genome or to physicians, and nothing it
describes is a clinical tool (Appendix~\ref{app:ruo}).

Researchers increasingly use AI coding assistants such as Claude Code and Codex
for this kind of work. When asked to analyze variants, these tools
typically generate a script: code that may fabricate
identifiers~\citep{shang2025geneturing}, attach the wrong PMID to a real
paper~\citep{bhattacharyya2023high}, cite a source that does not support the
claim~\citep{gao2023enabling}, reverse an allele, or bypass
established filters. Each session may produce slightly different code, and the
result must be reviewed for correctness, efficiency, and security before it can
be trusted. The output is a one-off answer tied to one session, not a reusable
resource.

This paper presents the Just-DNA ecosystem, which gives these same assistants a
different job. Instead of generating code, the assistant produces structured
data: a \emph{module} of editable CSV tables where each variant is linked to its
studies, citations, effect sizes, and supporting passages. The input can be
anything the assistant can read, from a single sentence describing a trait to a
collection of papers or a summary from another model. When the module is
enriched, and again when the registry publishes it, every variant's rsID is
resolved against Ensembl's variation records, which carry dbSNP identifiers.
Dedicated checking tools validate
gene symbols against HGNC, trait identifiers against ontology services, and flag
decisions that require domain expertise.
Once the module is compiled to machine-readable Parquet files, Just-DNA-Lite
joins it to a genome~\citep{companion2026justdnalite}. Modules are versioned and
shareable: they can be kept locally, rehearsed in a test registry, or
published for others to install and use. The same files can also be written or
edited entirely by hand.

This paper makes five contributions:

\begin{enumerate}
    \item It describes the module contract shared by manual editors, AI-assisted
    authoring tools, versioned stores, and the genome-analysis consumer.
    \item It presents \texttt{just-module-creator}, an authoring plugin that
    exposes the public capabilities of the ecosystem's format, compiler,
    enricher, and registry packages as typed Model Context Protocol (MCP)
    tools~\citep{anthropic2024mcp}.
    The plugin reads the installed schema instead of carrying a copy.
    \item It defines how modules move between a local store, a test registry
    whose publications can be deleted, and the public catalog while
    preserving their provenance and the
    decisions that still require review.
    \item It defines an evaluation protocol for variant recall, citation
    recall, and effect-direction agreement, compares the workflow with the
    same model working without the plugin on three papers, and reports catalog statistics
    from the first eight published modules across three independent namespaces.
    \item It reports a case study of an autonomous curation loop in which
    agent roles rebuild a longevity module over two weeks, coordinated through
    version-controlled files and event wake-ups, with human checkpoints that
    block only the work that depends on them (Section~\ref{sec:loop}).
\end{enumerate}

\section{Related work}
% ================================================================

\paragraph{Genome annotation and catalogs.}
A variant call records what differs between a sample and a reference genome.
Annotation adds information about that call, such as its predicted consequence,
known clinical classification, reported trait association, or the conclusion
assigned to a particular genotype. VEP, ANNOVAR, and OpenCRAVAT/OakVar perform
this kind of lookup by joining a callset to established
resources~\citep{mclaren2016vep,wang2010annovar,pagel2020opencravat}. ClinVar
and the GWAS Catalog publish records that can supply annotation
content~\citep{landrum2018clinvar,sollis2023gwas}, HGMD derives
variant--disease associations from the literature through manual
review~\citep{stenson2020hgmd}, ClinGen provides expert curation within the
ACMG/AMP framework~\citep{rehm2015clingen,richards2015acmg}, and ClinPGx
consolidates PharmGKB, CPIC, and PharmCAT into one pharmacogenomic
resource~\citep{whirl2012pharmgkb,clinpgx2025,clinpgxabout}. CIViC crowdsources cancer
variant interpretation, anchoring every evidence item to a source
publication~\citep{griffith2017civic}; its releases are database-wide rather
than installable per-topic units, which makes it a source this ecosystem
consumes rather than an alternative to it. The GA4GH Genomic Knowledge
Standards define interoperable representations for variant
annotations~\citep{ga4gh2022gks}. The problem addressed here begins before the
join: selected evidence must be turned into a reviewable, machine-checkable
collection that can be distributed and applied consistently.

\paragraph{Biomedical text mining and variant extraction.}
Conventional named entity recognition systems such as tmVar3 and PubTator3
have improved gene and variant tagging in biomedical
text~\citep{wei2022tmvar3,wei2024pubtator3}. LitVar~2 links literature
paragraphs with variant records from external databases, accelerating
knowledge retrieval~\citep{allot2023litvar2}. However, as the PubMind authors
note, these tools largely stop at tagging entities and do not recover relations
such as a variant's pathogenicity in a particular disease or the experimental
evidence behind a classification~\citep{wang2026pubmind}. PubMind applies
instruction-tuned LLMs to extract variant--disease--pathogenicity associations
directly from over 41~million PubMed abstracts and 5.4~million full-text
articles, producing a database of approximately 1.3~million unique variants
with contextual annotations~\citep{wang2026pubmind}. These systems demonstrate
that LLM-based literature mining can recover structured variant knowledge at
scale, but their output is a flat database rather than a versioned,
schema-validated module that an annotation consumer can install and apply to a
genome.

\paragraph{Factuality and tool use.}
Language models can produce fluent text that is unfaithful or
nonsensical~\citep{ji2023survey}, including references with fabricated or wrong
PubMed identifiers~\citep{bhattacharyya2023high}. A benchmark of genomic
question answering found confident but wrong answers across models and tasks,
among them gene name conversion and SNP locations~\citep{shang2025geneturing}. Retrieval-augmented approaches and
tool use reduce the need to improvise when a model can call a typed operation
instead~\citep{schick2023toolformer,jin2024genegpt}. The Model Context Protocol
provides a standard for connecting models to external
tools~\citep{anthropic2024mcp}. Biomedical MCP services can search literature,
ontologies, and variant databases. just-module-creator uses the same general
approach, then carries the result into module files that the rest of the
Just-DNA pipeline can inspect and reuse.

\paragraph{Agent orchestration.}
Multi-agent frameworks such as MetaGPT assign distinct roles to several model
instances~\citep{hong2023metagpt}. The plugin described here does not require
its own orchestration runtime. Claude Code or Codex supplies the agent, while
the plugin supplies the tools and the written workflow. This paper evaluates
that authoring path, not a particular choice of language model or agent-team
topology.

\section{Method}
% ================================================================

\subsection{The module artifact}

Before it is compiled, a just-dna annotation module is an editable
directory. It always contains
\texttt{module\_spec.yaml} and at least one recognized table. The table records
the thing being annotated, such as a genotype, a diplotype, or a measured
quantity. Evidence and machine-written sidecars (tables of records derived from
reference sources) are stored separately.
Compilation converts this human-readable directory into machine-readable
Parquet files and a content-addressed
\texttt{manifest.json}~\citep{justdnaformat2026}. The compiled artifact is what
a consumer installs and joins to a genome.

The authored files are ordinary YAML, CSV, Markdown, and optional image files.
A domain expert can open the tables in a spreadsheet to review and correct an AI
draft without special tools. just-module-creator
operates on this same directory rather than introducing a separate format for
AI-produced content. The module describes how a genotype or measurement should be
interpreted if a consumer encounters it. Just-DNA-Lite, or another compatible
consumer, supplies the genome or measurement later.

The author does not need to supply this directory, or any CSV file, at the
start of a session. Figure~\ref{fig:conversation-to-module} shows how a
conversation entry, which can range from a trait name to a collection of
papers, moves through routing, scaffolding, and review to a compiled module.
The \texttt{/create-module} router identifies the appropriate entry point
and stage.

On the sample path (Figure~\ref{fig:architecture}), Just-DNA-Lite converts VCF
input to Parquet and joins it with compiled modules in a streaming Polars join, producing
annotated reports and enriched data that the user can filter. With the ten modules of the companion paper's benchmark, the median time to
annotate a whole-genome VCF ranged from 33 to 65~seconds across its four call
sets on one workstation. The companion paper~\citep{companion2026justdnalite} describes the
sample path and polygenic risk score computation in detail.

Within \texttt{just-module-creator} the language model works on the
knowledge path: it searches, reads and drafts. VCF filtering, module joins and
polygenic scoring remain ordinary software steps with explicit inputs and
repeatable code. One optional command crosses to the sample path: when the
author asks, \texttt{/module-install-local} has the assistant run a module on
genomes held by a local Just-DNA-Lite and read which variants each genome
carries. The run goes through Just-DNA-Lite's own server, and the plugin's code
itself still opens no genome. Those per-genome results then reach the assistant's model provider.

\subsection{Determinism, evidence, and responsibility}

The compiler establishes structural validity and reproducibility: schema
conformance, coordinate resolution, and a deterministic content
signature~\citep{justdnaformat2026}. It does not establish whether the authored
claims agree with the literature: a false association in valid syntax
compiles without error. Three properties keep the evidence chain auditable.

First, authored values and their checks are kept independent. A value filled
from the source that will later check it makes the check compare that source
with itself: a quote taken from an article's title is found in that
article's own text. The design test is: \emph{could this check have failed?} If not,
it measured nothing (Section~\ref{sec:checks}).

Second, disagreements with reference archives are preserved rather than
silently resolved. ClinVar may lag a retraction; when the authored value
should remain, \texttt{record\_override} logs the difference and the reason.

Third, a check has three answers: it passed, it failed, or it never
ran. The third is recorded as a null, and a null is not a \emph{no}. The
identifier check writes an attestation to \texttt{verification.json} so a
reviewer can tell an empty report from one with no findings.

The assistant may locate a verbatim \texttt{provenance\_quote} from retrieved
full text and follow citations into supplementary tables to find per-variant
statistics. A \texttt{curator} field records who located each quote (a name
or model identifier) so a reviewer can direct scrutiny where it is most
needed. Attribution does not transfer responsibility: the human author holds
accountability regardless.

These records answer a reader's question of whether a published module
reflects its source or the assistant's reading of it only partly, and the
part they answer is where to look. Each study row can carry the passage it
rests on, verbatim, beside the PMID it was taken from; the \texttt{curator}
field says who located it; overrides of a reference archive are logged with
their reason, and the log is published with every compile. A reader who opens
the quoted passage can judge the row's claim against the source. Nothing in
the toolchain makes that judgment, and a free-text conclusion is the
assistant's or the author's wording, never the source's.

Curation follows drafting because a drafted row may still carry decisions the
source cannot make (genotype, weight interpretation, conclusion wording), and
these are surfaced for domain experts rather than resolved silently.

\subsection{Local and shared module stores}

A compiled module can reach a consumer through three routes
(Figure~\ref{fig:conversation-to-module}): local installation into a Just-DNA-Lite
checkout for testing with a VCF, publication to the test registry for a
deletable rehearsal, or publication to the immutable public catalog. The registry runs its own enrichment and
strict compilation on publish, so the stored artifact is the one the server
produced, not a locally claimed digest. Inclusion in either catalog
distributes a module; it is not scientific review, clinical validation, or
endorsement.

\subsection{Evaluation dimensions}

The plugin's scorer evaluates variant recall over
rsID--genotype pairs, citation recall (whether the run cites the papers the
reference cites), and
effect-direction agreement. Checking that a PMID names the intended paper is
not yet implemented in the scorer. The reference standard is a human
adjudication. On 31 August 2026 a bioinformatician read the differences
between two earlier runs of the same prompt on the same paper, which had come
out complementary rather than ranked: one agreed on every shared cell while
covering a third of the variant keys, the other covered every key and agreed
on a third of the cells. The reference takes the first run's studies and its
heterozygous row verbatim and the second run's two homozygous rows, and leaves
every weight blank, because no tool fills a weight and only a person settles
it. Scoring modules against a module the same system authored would measure
agreement with itself; the adjudication breaks that circle only in part,
because every reference row was first drafted by the system. The scored runs
came later and were not adjudicated: each cell is scored as the run left it,
and no disagreement between a run and the reference was resolved after
scoring. The prompt, the reference, the scored runs' files, and the scorer are
in the repository (Section~\ref{sec:code}), so every number in
Table~\ref{tab:scores} can be recomputed. The suite is not blinded in the
strong sense: the plugin's written guidance was developed by the same team
that built the reference.

Recall is reported at two
grains, because recovering the right variant with wrong genotypes and
recovering half the variants exactly are distinct failures that partial
credit averages away. \emph{Decoy rate} replaces precision: a variant
absent from one curation may still be correct, whereas a decoy is one an
expert designated non-associated.

the variant as stop-gained, which the study it cites classifies as intronic
at the same coordinate.

The one divergence is a significance verdict at $p \approx 0.07$, read as
\emph{suggestive} by two runs and \emph{not significant} by the third, which
an aggregate score would have hidden. Agreement also measures the guidance and not only the runs: the
validator names the missing genotype and a written rule states that a zero
weight is a claim where a blank is not, so convergence shows the workflow
is prescriptive, not that its output is confirmed.

A module can also be read without a reference curation, by checking what its
cells claim against what they withhold. That reading
corrected a prediction of ours: we expected a paper reporting no association
test to produce no variant rows, yet one run produced sixty. Each recorded
the observed allele but withheld effect direction and statistical
significance. The blanks are honest: with no association test, there was
nothing to report. Row count is therefore not part of the score; whether the
filled cells claim more than the source supports is.

\section{Results}

\label{sec:checks}

With the plugin active, the assistant calls typed tools
(Appendix~\ref{app:tools}) instead of generating code: enrichment adds
coordinates and derived sidecars, compilation validates against the live
schema, and the compiled artifact can be published to the registry and
immediately applied to a genome. The checks described in
Section~3.3 are meant to catch citation misattributions, identifier drift, and
schema violations, but an audit exposed a blind spot. The audit read working copies of four
catalog modules, authored under an earlier version of the workflow and not the
versions published in Table~\ref{tab:catalog}. In them, all 3,668
\texttt{studies.csv} rows carried the article's title as their
\texttt{provenance\_quote}, a passage that always matches its own full text and
evidences nothing. The quote check had never run on them.

The plugin can be installed in two commands, one adding its marketplace and one
installing it (\texttt{/plugin marketplace add} and \texttt{/plugin install} in
Claude Code, and the matching \texttt{codex plugin} commands in Codex). It
needs uv and Python 3.13 or newer. In version 0.27.0, the one Table~\ref{tab:scores}
evaluated, the assistant gains access to 60 typed
MCP tools (Appendix~\ref{app:tools}) and 20 skills---written workflow
instructions that teach the assistant when to call which tool. In both
Claude Code and Codex, skills marked as commands can be invoked directly
by typing \texttt{/name} in the prompt.

\subsection{Against the same model without the plugin}
\label{sec:baseline}

The workflow rests on the premise that an assistant working without these
tools produces less reliable records. We tested it in November 2026 by giving
the same prompt for three papers to one model under three conditions, one run
each, and repeating the nine runs with a second model: Claude Opus~5, then
Claude Opus~5.5, both through Claude Code. With the \emph{plugin} (version
0.48.20), the assistant ran from the plugin's repository with the tools and
the account's other connectors, as an author has them. With \emph{docs and
compiler}, it had the plugin's written guidance as plain documents and the
reference compiler, but no tools and no enricher. With \emph{examples and
paper}, it had two published modules as Parquet files and the paper's full

outside the repository, with no MCP server or plugin loaded, web access
allowed, and an instruction not to install or download code. Isolation was
read from each session's recorded tool calls rather than from its own
account. Three Opus~5 runs strayed: the examples-and-paper run on the

marked; one plugin run listed the names in the round's working directory

expert, and whether each cited passage supports its row's claim. With one run
per cell there is no spread, and two models through one host say nothing about
other hosts.

\section{Case study: an autonomous curation loop with human checkpoints}
\label{sec:loop}
% ================================================================

The sections above follow one assistant authoring one module with its author
at the keyboard. The same tools also serve a longer-running arrangement, in
which several agent sessions work on one module for days while the maintainer
is mostly away. We ran such a loop from 4 to 18 November 2026 to rebuild a
longevity module from its evidence. The module's first version is a port of
HAGR's LongevityMap~\citep{budovsky2013longevitymap}, which has not changed
since 2017. Most of its evidence is from candidate-gene studies, and more than
half of its study-cited variants rest on a single centenarian classifier whose
predecessor paper was retracted. The task was to re-read every locus against
its studies, add the genome-wide literature published since, and keep, re-tier
or drop each row according to what the papers show. The loop is a
non-blocking, asynchronous human-in-the-loop arrangement: the agents keep
working while the maintainer is away, and the maintainer's answers re-enter
the loop as events.

\paragraph{Structure.} The loop consists of standing roles. Each role is held
by one long-running agent session that has a written brief, a list of the
files it may change, and a statement of what it may push
(Figure~\ref{fig:loop}). The \emph{scout} searches the recent literature track
by track. It records every query with its date window and hit counts so that
the next sweep reruns the same query, merges a paper found through several
sources into one entry, and queues each paper that bears on an existing locus,
together with the passage that shows it. The \emph{curator} works locus by
locus and reads each article at the deepest level that decides the evidence
tier (full text over abstract, the supplement for per-variant numbers). For
every article it writes a note, which is never rewritten, only extended, and
which carries the verbatim quote each conclusion rests on and the depth at
which it was read. It then writes the locus row with its tier and evidence and
commits the row and its notes together. The \emph{module builder} exports the
curated rows into a module and runs this plugin's validate, enrich and strict
compile steps on each increment. It then rehearses the version on the test
registry. A \emph{coordinating agent} writes the repository's own checks
(every citation resolves to a note, and every quote is found in the article's
cached text or is reported as unknown), reviews the curator's rows in batches
against the papers, and settles questions of how a rule should be read. Two
support roles complete the set: a \emph{runner} submits bulk article fetches
as batch jobs on a compute cluster, and a \emph{liaison} tracks releases of
the plugin, compiler and registry and files defects with whichever project
owns them.

\paragraph{Interaction mechanisms.} No person relays work between the roles.
Three mechanisms take that place. First, \emph{state lives in documents}:
rows, notes, the queue, the progress list and each role's own notes are files
in one repository. A message only delivers news, and a message that reports
work names the commit that holds it. Before a session resets, the role
rewrites its notes to describe the current state, so the next session
continues from the files rather than from a transcript. Second, \emph{wake-ups
are events}. A watcher on a path wakes the role that consumes it whenever
another role pushes to that path. The scout's queue wakes the curator, and new
rows wake the module builder. A direct message from a named role also wakes
its addressee, while other traffic waits for the next turn. Third, \emph{write
surfaces are narrow}. The curator never edits the module specification, and
the module builder never edits a row. When a row does not compile, the module
builder sends it back to the curator with the locus and field named, and a
failure on the tool's side goes to the liaison with its reproduction. The
plugin's own rules (Section~3.3) bind every role that calls it: a PMID comes
from a search result, a hand edit is logged, and a check that could not run is
reported as unknown.

\paragraph{Non-blocking human in the loop.} The maintainer decides; the
maintainer does not operate the loop, and the loop as a whole never waits for
the maintainer. A question blocks only the branch of work that depends on its
answer. The role that asked files the question and goes on with everything
else, and the other roles continue unaffected. When the maintainer answers,
the answer is itself an event: a watcher on the question queue wakes the role
that asked, and that role resumes the blocked branch. Between answers the
system keeps running on its own, and the maintainer's attention goes only to
decisions. Four checkpoints connect the maintainer to the loop.
(i)~A \emph{question queue}. A question that the written requirements leave
to the module's owner becomes an issue that can be answered from a phone. Each
issue lists its options with their costs and a default. Two scope questions were
answered in this way: APOE is kept in this module and scored once, with one
result per $\varepsilon$ pair, and biological-ageing markers form an unscored
section. (ii)~A \emph{standing delegation}. Readings of the evidence rules
that the requirements left open were settled by the coordinating agent under
the maintainer's standing permission to proceed autonomously. Examples are
what counts as a replication, when a non-replication becomes a red flag, and
how a multivariate test supports a row. Each reading is recorded as a numbered
decision together with the alternative it rejected, so that the maintainer can
review and reverse it later. The repository holds 35 such decisions for these
two weeks. (iii)~\emph{Irreversible steps are reserved}. Only the maintainer
may publish to the production catalog or close the module. Every version
produced so far is a rehearsal on the test registry. (iv)~A \emph{shared
budget}. All roles run on one account and pause at 95\% of its usage window,
so that capacity remains for the maintainer's own work.

\paragraph{What it produced.} The rehearsal of 16 November held 164 rows. These
cover all 161 seed loci, which collapse into 156 rows, plus eight secondary
signals. Their tiers are A~15, B~73, C~41 and D~35, where D is the
negative-evidence layer that records a former claim that did not hold. The
rows comprise 489 variant rows and 679 study rows. All 245 rsIDs resolved,
with no reference-allele mismatch, and the module compiled under strict
resolution. By 18 November the corpus held 140 article notes, and the
repository held 1,171 commits, 674 of them the curator's.

\section{Discussion}
% ================================================================

Genomic data is becoming personally accessible, and people already use AI
assistants---coding tools such as Claude Code and Codex, or plain chat
applications such as ChatGPT---to interpret their
results~\citep[e.g.,][]{conyngham2026rosie}. Restricting this is not viable, so the more
effective response is to make the work happen in the open, where domain
professionals can review what others publish and the tools enforce structure. A
module is visible, reviewable, and correctable; a one-off chat session is none
of these.

The safety concern is real and extends beyond AI. Candidate-gene
associations with depression have failed to replicate in large
samples~\citep{border2019no}, and GWAS effect sizes are systematically
overestimated at discovery and shrink in replication
cohorts~\citep{palmer2017winners}. In direct-to-consumer raw data sent for
clinical confirmation, 40\% of variants were false
positives~\citep{tandyconnor2018false}, and misclassified variants have led to
genetic misdiagnoses that later reclassification
exposed~\citep{manrai2016genetic}. The ecosystem is therefore explicitly
research-only (Appendix~\ref{app:ruo}): a module that faithfully reflects a study that later fails to
replicate is not wrong on its own terms, but a user acting on it may be harmed
all the same. Deriving health conclusions from a person's genome calls for
expert care: a module records what studies report, its conclusions are
written for researchers, and interpreting an individual's result belongs to
clinical geneticists and genetic counselors.

The assistant reads untrusted text and can write to a registry, which gives
the workflow an attack surface. A paper may contain instruction-like text,
conflicting citations, or identifiers that are valid but wrong; a session may
attempt a registry action its author did not intend. The controls in place
are structural: registry writes require an account token, they go to the
deletable test registry unless the production catalog is named explicitly,
overrides of a reference archive are logged, and the registry recompiles and
re-enriches every module it accepts. None of these has been tested
adversarially. An evaluation with malicious papers, conflicting citations,
false-but-valid identifiers, instruction-like source text, and unauthorized
registry actions is future work.

Through the registry, a module one author publishes can be installed by
others. The plugin's MCP server uses the standard stdio and HTTP transports of the
Model Context Protocol, so other agent platforms that support the protocol can
call its tools. This work used only Claude Code and Codex. What travels through the registry is genomic-data-agnostic knowledge:
a module carries no individual-level data.

\paragraph{Limitations.}
The module system launched in August 2026. We are developing mechanisms to involve genetic counselors and
domain-expert agents in quality evaluation, and to communicate to citizen
scientists that many modules reflect early-stage research rather than
clinical-grade evidence. The evaluation's main gap is what it does not
measure: whether a cited source supports the claim a row makes. Free-text
conclusions are not scored at all, the assistant's judgment about support
remains a reviewer's question, and no support rate is reported; the comparison of
Section~\ref{sec:baseline} counts mechanical errors only (a nonexistent paper,
a dead rsID, a wrong position, a reversed allele), and no expert counted the
rows they would correct. The runs of Table~\ref{tab:scores} are three runs of
one prompt on one paper, a smoke test rather than evidence of reliability; the
comparison adds two papers and a second model but one run per arm and model,
all through one host, so the results say nothing about run-to-run spread or
host sensitivity, and two models of one family are not a survey of models. No retrieval-augmented arm was run, and the one reference
was adjudicated by a single curator.
Whether a module built this way yields correct annotations on real genomes is
the companion paper's subject and is not shown here.
The curation loop of Section~\ref{sec:loop} is a single run on one module with
one model family; its rows have not been compared with an independent human
curation, and production waits on the maintainer's review. Coordinates
are declared rather than translated, and the compiler is bound to GRCh38.
The file \texttt{module\_spec.yaml} names a \texttt{genome\_build}; an omitted one is
taken to be GRCh38, and a GRCh37 or T2T declaration is recorded while its
positions are still resolved as GRCh38. Liftover belongs
to the source or the consumer; the PGS Catalog~\citep{lambert2021pgs} already
distributes scoring files harmonized to GRCh37 and GRCh38~\citep{pgscatalogdownloads}. Runtime benchmarks are in the companion
paper~\citep{companion2026justdnalite}.

\section{Conclusion}
% ================================================================

Annotation knowledge produced in a chat session is lost when the session ends.
In the Just-DNA ecosystem, an AI assistant produces a versioned,
schema-validated module instead of a script, so the work survives review,
correction, and reuse by someone else. What makes that more than a file format
is what a module keeps separate: authored claims stay distinct from derived
records, a check that
could not run says so, and each row of a published module has a place for
the evidence behind it. Eight modules from three namespaces, three of them from authors
outside the development team, show the path is functional today; whether its
modules are correct is what the evaluation begins to measure. Against the same
model without the plugin, on three papers with two models, the difference was
not fewer invented citations, since no run invented any, but modules that pass
the format's validation and place their variants on a genome. The same
tools carry an autonomous curation loop in which agents do the reading and the
rebuilding and the maintainer is asked only for decisions, each rule the loop
applied written down for review.

The software is open-source and intended for research use only. It installs
in two commands in Claude Code or Codex, and a module drafted with it can be
reviewed in a spreadsheet and published for others to install.

\section{Research use only}
\label{app:ruo}

Annotation modules summarize published association findings. They are not
clinical-grade evidence. The authoring plugin does not make individual-level
predictions and does not open a genome. Just-DNA-Lite and \texttt{just-prs}
process sample data for research and educational use; their reports and scores
are not diagnoses or medical advice. Language that implies causation, such as
``causes'' or ``guarantees,'' is outside the scope of a module written with this
plugin. Interpreting an individual's results for health decisions belongs to
qualified professionals, such as clinical geneticists and genetic counselors.

\section{Plugin surface: tools and skills}
\label{app:tools}
% ================================================================

A Claude Code or Codex plugin is a bundle of two kinds of asset. \textbf{MCP
tools} are typed operations the assistant can call. Each has a name, typed
inputs, and a structured return value. \textbf{Skills} are written
instructions loaded into the assistant's context on demand; they teach the
workflow that the tools serve, including when to call which tool and what to
do with the result.

\subsection*{Tools (60, version 0.27.0)}

The tools are organized into a core set and nine optional groups. By
default all of them are listed; in an optional layered mode only the core set
is listed and a session reveals the other groups through \texttt{toolbox}.
Table~\ref{tab:tools-core} lists the 18 core and meta tools;
Tables~\ref{tab:tools-evidence}--\ref{tab:tools-closing} list the nine
groups. Registry writes require a token obtained through
\texttt{authenticate}. Requests to each outside service pass
through that service's pacing gate, and the literature search shares its NCBI
gate with the enricher, so both spend one NCBI budget.

\subsection*{Skills (20, version 0.27.0)}
